# Macro infrastructure

Date: 2026-10-19

Status: draft proposal for review; no implementation or verification is claimed.

Revision: incorporate ordinary Rock call syntax, `%derive` attachment, and
source-declared exports; adopt one lossless lexical input model with later
Rock-specific interpretation, including indented DSL blocks; grow a Rock-written
syntax library toward self-hosting without requiring full Syn-like coverage.

## Purpose

Make macros a usable, library-owned extension mechanism for Rock. The first
consumer is an expression-position formatting macro that can interpret a string
such as `"Hello {name}"`; derive macros are the next consumer of the same
infrastructure. Neither consumer should require compiler-owned formatting,
standard-library names, trait implementations, or special string syntax.
Indented, library-defined DSLs are an additional proof of the shared input model;
they must not require a compiler-owned HTML grammar or a second macro ABI.

This is a compiler-contributor specification, not documentation of current
language support. Syntax, manifest fields, SDK APIs, and commands identified as
proposed below describe the intended implementation contract. Delivery stages
are sequencing boundaries, not a second issue tracker; implementation work is
tracked in beads when available.

## Decisions and scope

- Keep `%` as the macro invocation sigil, shared by declarative and procedural
  macros; macro implementation kind does not change call syntax.
- Reuse ordinary Rock call syntax: `%path arg, arg`, with ordinary parentheses
  around ambiguous expressions rather than mandatory macro delimiters.
- Support `%path` followed by an indented input block, in item or expression
  position. Its contents need not be valid Rock tokens, literals, or expressions.
- Preserve source first in one lossless lexical stream for inline, block, and
  derive inputs. Rock token classification and balanced groups are interpretations
  over that stream, not prerequisites for delivering arbitrary block contents.
- Expand syntax before ordinary declaration collection and inference; macros
  receive lossless lexical data, not inferred types, resolved trait witnesses,
  or compiler HIR. Do not add separate token-input and raw-string-input APIs.
- Provide one token/provenance/hygiene model and one expansion scheduler for
  declarative, function-like procedural, and derive macros.
- Support authoring procedural macros in Rock through an explicit SDK dependency
  and a host executable generated by the build workflow.
- Put syntax parsing/AST construction in an ordinary Rock-written library, not
  compiler-prepared declaration views. Start with derive-input grammar; treat
  this library as a reusable foundation for a future self-hosted frontend.
- Declare procedural exports in source with `macro name = ...` and
  `macro derive Name = ...`; use ordinary `<` exports, not a manifest export list.
- Use ordinary `[dependencies]`; the dependency's target kind determines whether
  to build host macro code or program code. Keep those build/link roles separate.
- Use explicit imports and canonical identities, never a global bag of exported
  macro names or last-writer-wins registration.
- Add preceding `%derive Show, Eq` attachment after expression macros and the
  authoring path work; no Rust-style attribute syntax or general attribute engine.
- Do not add `f"..."`, a formatting language item, or a compiler builtin named
  `format`, `Show`, `String`, or a particular derive.

Not included: typed/semantic macros, arbitrary attribute transformations,
statement/type/pattern-position expansion categories, general compile-time
evaluation, an OS sandbox, persistent macro workers, expansion-result caching,
live compiler-service RPC, cross-crate declarative template publication, proc
facade re-exports/glob imports, unbounded inline DSL invocation syntax, full
Syn-like syntax coverage, a self-hosted compiler/lexer, or complete formatting,
derive, or HTML libraries. The infrastructure must prove the formatting, derive,
and bounded DSL consumers are possible without claiming those larger projects.

## Complexity review and first-delivery boundary

| Earlier requirement | Smaller sufficient design |
| --- | --- |
| Mandatory macro argument delimiters | Reuse Rock call boundaries and retain argument token slices |
| General annotation syntax for derives | One `%derive` directive attached to the next struct/enum |
| Manifest names, kinds, and implementation entries | Discover source macro declarations and ordinary exports |
| New target section plus macro-dependency section | Add `proc_macro = true` to `[lib]`; reuse `[dependencies]` |
| Worker requests lexer/literal services during execution | Supply literal views in the input and accept deferred source fragments in one final output |
| Full Syn-sized coverage or compiler AST projections as a prerequisite | Build one ordinary Rock syntax library, beginning with the grammar exercised by derives and shared compiler conformance fixtures |
| Separate raw-text and token macro entry contracts | One lossless lexical stream; Rock literals/groups are optional interpreted views, and block boundaries are compiler syntax |
| New stable, language-independent transport architecture | Evolve the existing bounded, version-locked request/response protocol |
| General artifact-envelope redesign | Extend existing products/descriptors with only the proc-only distinction needed by validation/linking |
| Exported declarative environments and proc facade closures as prerequisites | Deliver direct proc dependencies and source-module declarative macros first |
| General incremental expansion/dependency engine | Deterministic bounded module passes/work queue, without persistent scheduling infrastructure |

These are scope reductions, not permission to skip validation, hygiene, source
locations, correct host selection, or worker cleanup. Deferred features must
receive clear unsupported-feature diagnostics, not partial silent behavior.

The lossless frontend is a deliberate expansion of scope after this complexity
review, not a small lexer fallback or another scope reduction. It requires a
new preservation/interpretation boundary and a dedicated delivery gate. Reuse
Rock's current lexical behavior in its Rock-specific interpretation layer;
do not claim that the current lexer can already supply arbitrary DSL input.

## Current implementation baseline

The repository already has useful components, but not an end-to-end authoring
workflow:

| Area | Observed implementation | Required change |

Token provenance is not identifier hygiene. An enum case named `DeriveLike` is
not derive support. A manually constructed proc-macro artifact in a test is not
a usable package workflow. These distinctions are completion requirements.

## 1. Invocation syntax and expansion categories

### Ordinary-call expression invocations

The proposed expression syntax is `%macro_path arg, arg`, where `macro_path`
follows ordinary Rock module path spelling. Reuse the ordinary call parser's
argument boundaries, comma handling, indentation, and grouping rules. Record
the original argument token slices and separators as macro input; syntax parsing
does not evaluate arguments or require their names/types to resolve.

This proposed complete source example uses a local declarative macro:

```rock
macro identity
    $value:expr =>
        $value

main = !->
    answer = %identity 42
    answer.println!
```

- Parse an invocation wherever a primary expression is allowed, including call
  arguments, lambda bodies, array elements, initializers, and nested expressions.
- Its result is exactly one expression. Surrounding operators, postfix operations,
  and nested-call argument ownership follow ordinary Rock call parsing; no
  macro-specific greediness or arity lookup determines where input ends.
- Use ordinary parentheses to disambiguate an argument or the complete macro
  expression in an enclosing call. `%m (a + b)` groups one argument; `(%m a, b)`
  groups the whole invocation. Do not assign adjacent `%m(a, b)` a separate
  Rust-style argument-list meaning.
- Reuse ordinary zero-argument call syntax, `%m!`, in expression position.
- Ordinary-call inputs must be syntactically valid Rock arguments even when the
  worker will discard them. Non-Rock DSL input uses the explicitly bounded block
  form below, not an unbounded inline grammar guessed by the parser.
- Require full consumption of the generated expression stream; reject empty
  output, multiple independent expressions, stray declarations, and trailing
  tokens rather than accepting a valid prefix.
- An expression result may contain an ordinary block expression, including
  bindings and a tail value. Do not introduce a macro-only block representation
  or wrap output in a lambda, which would change `return`, `break`, and borrowing.
- A macro used as an expression statement still has expression semantics; this
  does not introduce a separate statement-list output category.

### Indented input blocks

A bare `%macro_path` ending its header line, followed by a more-indented nonblank
line, captures an input block. This form is available in expression and item
positions for either macro implementation kind. It does not parse the block as
ordinary call arguments, infer arity, or choose syntax based on a macro's output.
The following is an invocation fragment; `html` is a user-supplied macro whose
input language and output value are library-defined:

```text
page = %html
    <div>
        Hello, world! 👋
        Don't interpret // as a Rock comment or require this ( to close.
    </div>
```

- Recognize the header only in actual Rock syntax. A `%html` spelling inside an
  ordinary Rock string/comment is not an invocation. Do not identify all blocks
  with a context-free regex prepass over file text.
- Compare physical line indentation with the invocation header's enclosing line
  indentation. The first following nonblank line must be more indented. Capture
  until the next nonblank line at that header indentation or less, or EOF; that
  dedented line is not input. Blank lines between header and body and within the
  captured range are retained. A blank line means whitespace-only, not a DSL
  line that happens to look like a Rock comment. The original input range starts
  immediately after the header's line ending and ends at the start of the
  terminating dedented line, or EOF, retaining all intervening line endings.
- Use the ordinary source indentation policy with checked widths, retaining its
  exact spaces/tabs and line endings. Never wrap a width through `Indent(u8)`.
  Header/base indentation is available as metadata; do not silently dedent,
  trim, normalize, or erase the original block spelling. Body indentation is
  data: do not impose Rock expression-layout rules on its internal lines.
- Establish that boundary before interpreting body quotes, comments, or
  delimiters as Rock. None of them may consume a following dedented Rock line.
  Unmatched quotes/brackets, unfamiliar punctuation, Unicode, and comment-like
  text are preserved within the boundary. Arbitrary input means valid UTF-8
  within the block and resource limits, not arbitrary bytes or permission to
  cross its terminating dedent.
- `%m!` remains the explicit zero-argument expression call and cannot also own
  a block. A bare `%m` with a more-indented body always means block capture;
  multiline ordinary arguments must use an ordinary-call header with an argument
  or grouping, not compete for that spelling. A bare `%m` without a body is
  still allowed as an existing zero-input item invocation, not an implicit
  zero-argument expression; an empty block cannot be distinguished from no body
  and is not separately introduced. `%derive` retains its reserved attachment grammar.
- Inline arguments plus a separate DSL body are not added in this delivery.
  Block capture itself does not recognize nested macro calls: apparent `%m`
  text inside belongs to the outer macro until emitted as Rock syntax.
- Input shape and output category are independent. A block in an initializer
  must return one Rock expression; a module-scope block must return items. The
  same `MacroContext, TokenStream -> MacroResult` entry contract receives all
  inputs; block spelling is not a separate raw-string variant or macro kind.

The compiler owns only the invocation boundary and expansion contract, not HTML,
SQL, template interpolation, text whitespace policy, or another DSL's grammar.
For example, an HTML macro decides whether bare `Hello` is text or a reference.

### Item invocations

Keep existing item-only line invocations, including zero-argument `%make_main`
and existing declarative matcher input, and add the indented-block boundary
above. Item-line input need not become an ordinary expression argument list;
outside an explicitly captured block it retains Rock lexical interpretation.
They enter the same expansion engine, requesting zero or more ordinary top-level
items; output category is not a reason to invent another SDK input model.

Expression and item positions are distinct requested output categories, not
alternative parsers tried until one succeeds. A function-like proc export may
serve either category and receives the requested category in its context.

Within the supported direct-import scope, qualified invocations and category
failures must work for either implementation kind. Unsupported type/pattern
invocation positions receive explicit diagnostics rather than reaching lowering.

### Derive attachment

Use a preceding `%derive path, path` directive for one struct or enum declaration.
`%derive` is a reserved attachment mechanism, not an implicitly loaded std macro
or an ordinary user-defined function-like export. Each listed path resolves in
the macro namespace to a `DeriveLike` export; its name need not match a trait.

The syntax shape is `%derive Show, Eq` followed by the declaration on the next
nonblank/noncomment line in the same scope. Blank lines/comments are allowed;
another declaration/import/invocation cannot intervene. Consecutive `%derive`
directives accumulate in source order on that declaration. Missing/unsupported
targets and empty derive lists are errors.

This adds a small attachment AST, not a general annotation system. Rust-style
`#[derive(...)]` and arbitrary attribute transformations are outside the grammar.
Prevent declaration/export of a function-like macro named `derive` so its
unqualified spelling cannot silently change the directive's interpretation.

- Each derive receives the original declaration token tree, including fields,
  variants, generic binders/defaults, bounds, visibility, and source contexts,
  plus its own attachment location. It may parse those tokens with the ordinary
  syntax library in section 6; the compiler sends no declaration AST, inferred
  field types, or reflection data.
- Strip all attached `%derive` directives from executable input. All derives
  on one declaration inspect the same original declaration, not each other's
  output; no generic attribute metadata or reflection interface is needed.
- Preserve the original declaration exactly once; append each derive's item
  output immediately after it, in attachment/list order. Empty output is valid.
- A derive cannot replace/delete its input declaration. Duplicate impls,
  incoherent bounds, and privacy violations fail through ordinary checking.
- Consume an attachment once per declaration-node identity, not once per span.
  Generated declarations may themselves have derives and enter the same queue.
- Reject derives on functions, aliases, traits, or other unsupported targets;
  reject duplicate canonical derive identities on one declaration.

Actual `Show`, equality, clone, or serialization derives are library follow-up
work, not builtins or completion claims of this specification.

## 2. Expansion, modules, and macro name resolution

### Macro namespace

Use a macro namespace separate from values and types, reusing ordinary module
visibility and explicit import/export path handling. Existing `>` and `<` forms
bind macros too; `%` invocation and derive paths select this namespace. A macro
and a function may share a spelling without ambiguity.

- Macro definitions are module items, visible throughout their module,
  independent of textual declaration order; block-local macro definitions are
  not added by this change.
- Resolve qualified paths against explicitly supplied dependency identities and
  loaded source modules. Preserve aliases supported by the ordinary importer.
- Conflicting declarations/explicit imports are errors, not overwrites. Do not
  add macro-specific shadowing rules or auto-import every loaded export.
- Exporting a proc declaration uses ordinary `< name` or inline export syntax.
  Source-module declarative imports use existing source-module visibility rules;
  external publication of their templates is deferred.
- Macro glob imports and facade/re-export chains are deferred. Ordinary value/
  type globs are unchanged; a macro use depending on a deferred binding gets a
  specific diagnostic. Do not require a second general-purpose glob resolver.
- Proc exports are available only through their declared package/module surface;
  merely loading a dependency artifact does not inject every export unqualified.
- Never choose between a declarative and procedural export by implementation
  kind. A conflicting binding is an error regardless of which implementation
  happened to be registered first.
- Canonical identity includes the supplying crate identity and export identity;
  user-facing spelling, absolute filesystem paths, or hash-map iteration order
  are not identity authorities.

For this delivery, external proc macros come from direct declared dependencies,
with explicit imports or qualified calls. Serialize their discovered exports in
the existing proc descriptors. Exporting declarative templates across artifacts
needs definition-environment serialization and is deferred; diagnose that case
instead of claiming proc descriptors already implement it.

### Bounded fixed point

The frontend must interleave source-module discovery, macro import resolution,
and item expansion before ordinary declaration collection:

1. Load explicitly supplied artifact interfaces without executing macro code.
2. Parse available modules and discover source macro definitions and imports.
3. Resolve and expand ready item invocations/derive attachments in stable module
   and source order; load generated module declarations and discover newly
   generated macro definitions/imports.
4. Repeat discovery/item expansion until no more ready work exists. Diagnose
   unresolved paths, import cycles with no progress, or exhausted limits.
5. Expand expression invocations throughout the resulting modules, outside-in;
   recursively expand returned expressions until none remain.
6. Run ordinary declaration collection, operator resolution, lowering, inference,
   MIR/borrow checking, monomorphization, and code generation.

Do not pre-expand macros inside the captured lossless input of another macro: the outer
macro controls whether that input is copied, inspected, discarded, or expanded
later. Item output discovery must complete before a body is diagnosed for a
missing macro import that a generated item may provide. Expression output
cannot introduce module-scope declarations/imports through a side channel.

Use stable invocation/node identities and explicit parent expansion edges;
spans may repeat when a capture is duplicated. Expansion errors must retain the
actual invocation ancestry, not the most recent unrelated expansion.

Implement these rounds with deterministic module passes or a small work queue;
no persistent incremental graph or general dataflow scheduling framework is
required. Never execute a resolved invocation again merely because a later pass
discovers another module/import.

Depth limits alone are insufficient: enforce finite total invocations, output
tokens/bytes, matching work, and source-module discovery. Failures must be
diagnostics, never a panic, infinite retry, or silently unexpanded node.

On success, no invocation or unconsumed derive attachment reaches ordinary
lowering. Keep a strict internal check at that boundary.

## 3. Lossless lexical data, Rock interpretation, and declarative expansion

### Preserve first; interpret afterward

Replace the assumption that macro input must already consist of valid compiler
tokens. Introduce a shared, lossless lower-level lexical representation and put
Rock-specific token classification above it:

```text
Source snapshot
    -> lossless lexical stream, with exact spelling and origin/context segments
        -> Rock interpretation -> Rock tokens/groups -> current syntax parser
        -> macro input -> SDK/library-defined interpretation
Macro output
    -> same lossless representation -> Rock interpretation/capture -> syntax parser
```

`TokenStream` remains the proposed public name, but its leaves are no longer
defined by today's compiler `TokenType` enum. The SDK/compiler are version-locked;
this is not a new permanently stable token ABI. All invocations receive the same
representation, whether capture boundaries came from ordinary arguments, an
indented block, an item line, or a derive declaration. Do not add `RawBlock` versus
`Tokens` request variants, a special text-macro entry signature, or mandatory
string-literal wrapping for DSLs.

The preservation layer must:

- Cover every byte of accepted UTF-8 source in order, including whitespace,
  comments, line endings, quote characters, and otherwise unsupported symbols.
  Exact reconstruction from retained spellings must equal the captured input;
  reconstruction is an inspection property, not a way to forward syntax.
- Use neutral lexical units/runs without requiring Rock literals/comments to
  terminate or delimiters to balance. Classification hints, if supplied, are not
  validation or an authority to discard text. An unknown Unicode character or
  embedded NUL is data here, not `UnknownToken` or an EOF sentinel. Invalid UTF-8
  at source ingestion and resource exhaustion remain explicit errors.
- Preserve byte ranges, adjacency, physical layout, and source/expansion origins.
  Retain syntax-context segments even before text is interpreted as identifiers;
  source locations alone never authorize a caller binding.
- Support exact slices and structural splices without requiring a file read,
  guessed gap text, or print/re-lex cycle. Cuts must respect UTF-8 boundaries and
  retain the applicable metadata. Count stored spelling and trivia in budgets.

The physical leaf/run partition is an implementation choice, not a new language
grammar. Do not force one allocation per character; do require deterministic,
bounded scanning and complete source coverage. A partial literal or comment may
not prevent preservation of subsequent text or hide the block's dedent.
Interpretation must follow retained text/adjacency, not assume each neutral leaf
is already one Rock token. Library consumers must be able to traverse or slice
a run even when its boundaries differ from their own grammar's token boundaries.

### Rock interpretation and optional groups

The Rock-specific layer recognizes today's literals, identifiers/keywords/types,
operators/adjacency distinctions, comments, layout, and special tokens. It may
ignore trivia in its parser view, but the underlying stream retains it. Reuse
the current language rules, not the current destructive filtering architecture;
ordinary programs must retain their existing syntax, operator behavior, and
diagnostic precision. This change does not make every character legal Rock.

Interpreted literals and balanced parenthesis/bracket/brace groups are useful
views, not conditions for representing arbitrary input. A consumer requesting
Rock syntax gets errors for malformed Rock literals/groups; a DSL consumer may
treat the same apostrophe or unmatched `(` as text. Do not require a successful
Rock group/literal pass just to invoke the latter. Group views retain opening/
closing ranges and underlying units, so inspection never loses source spelling.

The compiler's Rock view must reach an invocation header before interpreting
its captured body. Scanning the complete file into neutral units is fine;
strictly interpreting the complete file as Rock before parsing is not. Replace
the eager `lexer.collect()` contract in `parse_source` with a capture-aware
interpretation/cursor boundary. Outside macros, quoted/comment contents still
obey Rock rules; this is not a global search for macro-looking text inside them.

Preserve existing identifier contexts when classifying captured units into Rock
identifiers. Reclassification is not permission to mint call-site authority.
Views may subdivide syntax while retaining provenance/context, but must not
silently merge conflicting contexts into one binding. Explicit construction of
new identifiers uses the hygiene operations in section 4.

### Output validation and layout

Validate transport structure, authorized contexts/origins, explicit group
integrity, UTF-8 ranges, and budgets recursively. Reject forged EOF/control
markers; a source NUL leaf is not such a marker. Then interpret and parse the
output as the requested Rock category, recognizing any generated macro-block
boundaries before their bodies are interpreted. Forwarded arbitrary text is
legal inside a generated block; the same text in ordinary Rock syntax must
pass normal lexical/syntax validation. Do not globally reject all unmatched
delimiter characters before capture-aware parsing gets that opportunity.

Do not infer layout by printing and lexing captured streams, or unconditionally
discard indentation/EOL as the current item invocation parser does. Rebase
generated Rock item/expression-block layout with checked arithmetic while
retaining original spellings and mappings. Relocation must move a captured DSL
block's enclosing margin consistently without rewriting its internal payload;
do not apply Rock body-layout validation to DSL text. Explicitly constructed
groups must be internally well formed even though ungrouped lexical leaves need
not balance: check explicit wrapper structure, not blanket balancing of every
character in its payload. Structural splicing preserves token separation and
opaque capture boundaries; do not accidentally glue identifiers/operators by
forgetting their adjacency metadata. Source preservation alone never certifies
valid generated Rock.

### Declarative expansion

For declarative macros:

- Retain existing matcher/template syntax and first matching arm order; an arm
  must consume the complete input to succeed.
- Existing identifier/type/expression matchers and template syntax use a Rock
  view over the shared input, ignoring trivia only according to that matcher
  contract. Retain exact underlying slices for captures. Merely delivering a
  block does not add an arbitrary-text matcher or change a DSL into Rock; an
  unsupported/mismatched declarative input gets a structured diagnostic.
- Preserve each capture occurrence and its context; equal token spelling does
  not justify deduplicating distinct captures or source locations.
- Match `expr` using Rock's syntax parser with the current parser configuration,
  never with inferred types or hardcoded std operators. Forward expression
  captures as grouped/opaque expression fragments so substitution cannot alter
  their precedence, and retain those fragment boundaries through nested macros.
- Keep the current single-type-name `ty` meaning explicit; parsing arbitrary
  type fragments is not silently bundled into this work.
- Flat repetition must make input progress and preserve independent capture
  occurrences; diagnose mismatched capture lengths and ambiguous matches.
- Nested repetition is not required for this delivery. Reject unsupported
  nesting at definition validation instead of producing flattened wrong output.
- Reuse token trees, generated parsing, diagnostics, and hygiene for both result
  categories; do not build a second expression-specific macro engine.

## 4. Hygiene and definition-side references

Introduce syntax contexts that participate in name binding/resolution. Source
spans remain diagnostic data and cannot grant binding authority.

| Origin/API operation | Resolution behavior |
| --- | --- |
| Forward captured token | Preserve its existing caller/outer-expansion context |
| Interpret/slice captured lossless units | Retain origin/context segments; recognizing an identifier does not create new authority |
| Literal-derived expression tokens | Explicit invocation-site context, with literal subspan provenance |
| Declarative template-local binding | Fresh expansion context; references emitted from that template agree |
| Proc-generated local identifier | Fresh context by default; reuse the minted identifier for its references |
| Explicit call-site identifier | Intentionally resolves/binds at the invocation site |
| Definition-side path | Resolves against the provider's recorded dependency environment, not caller spelling |

Template free names resolve in the definition environment; captures resolve in
their original environment. Generated item names follow the same rule unless
explicitly exposed: declarative macros use captured identifiers for public names,
and proc macros use the SDK's explicit call-site name constructor. A derive
references its input type through captured tokens, not a regenerated bare name.

Freshness is identity-based, not a `__macro_123` naming convention. Carry contexts
through token flattening, AST identifiers and paths, patterns/bindings, module
lookup, lowering, and diagnostics. Context must not disappear when constructing
an ordinary identifier or formatting debug text. Do not build cross-crate context
serialization for deferred declarative exports as a prerequisite.

Provide a definition-crate/path operation equivalent in purpose to a hygienic
crate reference: an exported macro must still find its public runtime helpers
when dependencies are renamed or a caller declares a same-spelled local module.
Definition-site resolution does not bypass visibility, orphan/coherence rules,
unsafe checking, or declared dependency requirements. Private runtime helpers
are not made public by expansion.

The compiler mints/validates context and dependency handles. Proc output cannot
forge compiler `DefId`s, claim arbitrary source files, borrow another invocation's
handles, or obtain access by inventing a crate name/context integer.

## 5. Rock procedural-macro authoring and build graph

### Proposed manifest surface

Add `proc_macro = true` to the existing `[lib]` target. This marks a host-only
macro library; reject a nonboolean flag and combinations with `[[bin]]` for this
delivery. Keep macro implementations separate from runtime helpers. No separate
target table, dependency table, or manifest export registry is needed.

Example proposed macro package `demo_macros/rock.toml`:

```toml
[crate]
name = "demo_macros"
version = "0.1.0"

[lib]
path = "src/lib.rk"
proc_macro = true

[dependencies]
rock_macro = { path = "../rock_macro" }
```

`rock_macro` is the proposed ordinary Rock SDK package, not an automatically
registered compiler crate. In this example its source package must be present
at the declared sibling path. Authors declare implementations in source and
export them through ordinary Rock visibility:

- `macro name` followed by matcher arms remains a declarative definition.
- `macro name = context, input -> ...` defines a function-like proc macro.
- `macro derive Name = context, declaration -> ...` defines a derive proc macro.

The last two forms are proposed new syntax allowed only in a proc library.
They declare ordinary host function bodies with SDK entry contracts plus macro
kind/name metadata; no proc macro executes to discover those declarations.
Discover declarations after source macro expansion, then generate/validate the
dispatcher. Private implementations may remain local, but only exported macro
declarations appear in the consumer interface. Duplicate names, wrong signatures,
and invalid export/target combinations are errors. Ordinary helper functions
remain ordinary functions, not implicitly exported procedural macros.

Proposed complete `demo_macros/src/lib.rk`:

```rock
> rock_macro::MacroResult

macro identity = context, input -> MacroResult::Expand input

< identity
```

The dispatcher supplies the typed context and shared lossless token stream;
unused `context` is intentional. The proposed SDK result includes
`Expand(TokenStream)` and an error-diagnostics result, expressed using ordinary
Rock enum construction.

Example consumer `app/rock.toml`:

```toml
[crate]
name = "app"
version = "0.1.0"

[[bin]]
path = "src/main.rk"

[dependencies]
demo_macros = { path = "../demo_macros" }
```

Proposed complete `app/src/main.rk`:

```rock
> demo_macros::identity

main = !->
    answer = %identity 42
    answer.println!
```

The proposed authoring workflow is `rock build` in the macro package, then
`rock run` in the consumer, using the normal CLI's std selection policy. SDK
dependencies and host std artifacts are still explicitly supplied to `rockc`
by the build orchestrator; the compiler does not discover either itself.

### Host and runtime dependency separation

- Use `[dependencies]` with the existing locator rules. Inspect the supplied
  library target kind to determine its role; do not make authors repeat that
  information in a second dependency list.
- Build a proc target and its ordinary library dependencies for the compiler's
  execution host, not the generated program's target. A proc library's proc
  dependencies are built first; its ordinary dependencies are host libraries.
  Diagnose cycles through the existing build graph with the involved packages.
- A proc dependency imports no runtime values into the program. Reject attempts
  to import its implementation functions as runtime values, and never pass its
  host objects or SDK dependencies to the program's linker. Generated
  references to runtime helper crates require declared ordinary dependencies;
  missing ones receive a diagnostic naming the required dependency identity.
  Record runtime helper requirements as logical crate/export identities and
  validate them against the consumer's target interfaces; never reuse host-side
  `DefId`s, layouts, or object files as target-side binding authority.
- Proc facade re-exports and their transitive artifact closures are deferred;
  use direct macro dependencies and diagnose an attempted unsupported re-export.
- Extend existing build identity/freshness checks with macro/ordinary role and
  host/target distinction. Retain compiler/options/source/dependency inputs;
  do not design a new build cache or reuse target objects as host dependencies.
- The macro implementation package cannot expand itself using its own not-yet-
  built executable. Diagnose cycles with a dependency chain.

The generated executable contains a dispatcher and SDK transport runner; authors
do not implement framing, stdin/stdout handling, or a handwritten export table.
Bootstrap it using ordinary Rock code and an explicitly available SDK, without
requiring a proc macro to build the first proc macro. A Rust-only fixture host
is useful for tests but does not satisfy Rock authoring acceptance.

### Compiler/artifact boundary

Keep `rockc` artifact-only. Publish discovered exports through the existing
`CompilerProducts.proc_macros`/artifact machinery and pass them through
`--extern-artifact name=path`, not source package paths or bare executable flags.
Add only the explicit proc-only distinction needed by artifact validation and
linking: a proc-only artifact describes a host executable and has no target
object or ordinary runtime exports. Do not satisfy runtime validation with dummy
object files, weaken ordinary library checks, or redesign the artifact envelope
as a general multi-payload framework.

The macro build packages that artifact plus its executable and required runtime
files. Source/build orchestration belongs in `rock`; compiler macro semantics,
validation, and expansion belong in `lib`; manifest definitions in `rock-shared`.

Descriptors record canonical crate/export identities, kind, protocol/compiler
compatibility, host triple, executable content identity, and required host files.
Resolve relative executable paths against the artifact location, not the current
working directory; validate before spawning. Packaging/relocation must preserve
identity and verify the selected executable. Loading/inspecting an artifact is
not permission to run every exported macro: execute only a resolved invocation.

Bump affected artifact/protocol versions as needed. Rebuild dependencies and
reject obsolete formats; do not add compatibility readers or transitional aliases.

## 6. SDK, literal inspection, and deferred source fragments

The SDK exposes ordinary Rock data/APIs for lossless lexical streams, optional
groups/layout/literal views, identifiers, opaque source/context handles,
diagnostics, and expansion results. The conceptual entry contract is
`MacroContext, TokenStream -> MacroResult`; kind and requested output category
are in the context. No compiler
AST/HIR data structures become the public ABI.

### SDK scope and public model

Separate the compiler-facing SDK from optional library-owned syntax trees. The
SDK is not a Rock compiler written in Rock; the syntax library intentionally
implements a growing subset of Rock's syntax grammar, not semantic analysis:

| Layer | Responsibility |
| --- | --- |
| Compiler, currently implemented in Rust | Preserve source in neutral lossless units, interpret Rock syntax/capture boundaries, supply metadata and already recognized literal views, parse expanded output, and perform semantic checking; no declaration AST payload |
| SDK, ordinary Rock library plus generated transport runner | Own/iterate/copy/splice the shared lexical data, expose exact spelling, construct output, collect diagnostics, encode/decode the version-locked request/result |
| Syntax library, ordinary Rock code | Interpret available lexical units as supported Rock tokens/groups, parse library-owned AST nodes, expose structural manipulation, and emit syntax without compiler callbacks |
| Quote-style helpers | Convenient token construction and interpolation of existing syntax; start with ordinary constructors/emission helpers rather than requiring a full quotation language |
| Macro author | Recognize the macro's input contract, choose what code to emit, preserve/splice input tokens, and implement domain-specific policy such as formatting or deriving a test trait |

Proposed public types describe the new preservation/interpretation boundary,
not a small projection of today's compiler `TokenType`:

| Type | Contents and contract |
| --- | --- |
| `TokenStream` | One lossless ordered stream for all input shapes, retaining exact spelling/layout, metadata segments, optional group views, and opaque expression-capture boundaries |
| `TokenTree` | A lossless lexical leaf or explicit/interpreted group/capture; leaves may include characters that are invalid or unmatched in Rock; output additionally permits deferred source fragments |
| `Token`, `TokenKind` | Neutral lexical unit/run with exact spelling, byte ranges, adjacency, and origin/context segments; Rock-specific classifications are views rather than required source validity |
| `Group`, `Delimiter` | Optional parenthesis/bracket/brace interpretation with opening/closing ranges and nested stream; group construction/interpretation does not erase underlying units |
| `Identifier` | Spelling plus binding context; copying preserves identity, and changing spelling is an explicit construction rather than raw integer/context mutation |
| `Span` | Opaque source-location handle with checked byte-range operations, not arbitrary file access or binding authority |
| `LiteralView` | Already Rock-recognized literal's original spelling, canonical decoded value, source mapping, and input handle; not automatic classification of arbitrary DSL quotes |
| `MacroContext` | Kind/category, invocation span, authorized construction operations, optional ordinary-argument slices, and capture indentation/ranges; no raw-versus-token payload switch, compiler AST, or semantic lookup |
| `MacroResult` | An output stream or structured failure diagnostics; warnings/notes collected in context travel in the same final response |

All views are owned request data or local views into that data; reading them
does not contact the compiler. Source/context handles are authorized only for
their owning invocation; copying or storing them grants no authority in another
request. Ordinary SDK types may be copied according to Rock's ownership rules;
copying a token must preserve its context and provenance, not mint a new binding.
No general editable syntax-object graph or remote object handle API is required.

The SDK should offer the following small set of operations; the names below are
proposed API contracts, not claims about an existing implementation:

| API | Behavior |
| --- | --- |
| Stream iteration/indexing, `push`, `extend`, checked slices | Traverse/assemble lossless units or existing groups, preserving spelling/order/metadata; unmatched punctuation remains inspectable |
| Exact spelling and checked source slices | Read retained text/trivia locally for any input shape, without a raw-block API, filesystem access, or loss of the structured stream |
| `TokenStream::group delimiter, body, span` | Return a stream containing a balanced group; reuse `body` tokens unchanged |
| A small lexical cursor with peek/consume/group access | Local convenience over units and already available groups, not an implicit validating Rock lexer/parser |
| `context.expression_arguments!` | Optional slices from ordinary call parsing; absent for block/item inputs, zero entries for a zero-argument expression invocation; every slice uses the same stream type |
| `context.fresh_ident spelling`, `context.call_site_ident spelling` | Explicit fresh-local or caller-binding construction; fresh handles are symbolic invocation-local data validated by the compiler on return |
| `context.dependency_path ...` | A validated definition-side path into an authorized dependency's public interface; not a raw compiler identity |
| `context.literal_view literal` | Read the already supplied literal view; no decoding implementation or RPC in the worker |
| `TokenStream::literal_fragment literal_view, range` | Emit a checked literal-substring descriptor for later compiler tokenization in invocation-site context |
| `TokenStream::source_fragment text, context` | Emit generated text with an authorized context, not an immediately parsed/inspectable token stream |
| `context.error span, message` and diagnostic builders | Collect structured errors/labels/notes; the runner returns them without authors writing transport code |

Use the argument views rather than splitting on every comma in a flat stream:
commas inside groups and ordinary Rock nested-expression syntax already belong
to the compiler's call parser. Generic cursor helpers must not masquerade as a
complete expression parser. Captured expression-fragment boundaries remain
opaque/preserved even when a macro iterates the containing stream.

A DSL macro can inspect exact spellings or build a local parser over the same
units, including whitespace, apostrophes, and unmatched punctuation. A Rock macro
can request the supported Rock interpretation/parser helpers in `rock_syntax`.
These are library views over one input representation, not alternate entry
contracts or a demand that every macro implement Rock's grammar. Merely reading
source text does not strip contexts from the original stream; forwarding must
reuse that stream or explicit authorized construction, not re-emit its spelling.

For example, this proposed complete proc-library source wraps its input in a
parenthesis group without parsing, printing, or evaluating it; the package uses
the SDK dependency and proc-library flag from section 5:

```rock
> rock_macro::Delimiter
> rock_macro::MacroResult
> rock_macro::TokenStream

macro grouped = context, input ->
    output = TokenStream::group Delimiter::Paren, input, context.invocation_span!
    MacroResult::Expand output

< grouped
```

The compiler subsequently checks that the emitted group is legal in the
requested output category. Domain-specific input restrictions belong in the
macro's validation. A general quote/template language is not needed to bootstrap
this API; start with stream/group/token constructors and preserved splices.

### Incremental syntax library written in Rock

Use `rock_syntax` as the working package name for a Syn-like ordinary library;
the name is not a compiler-known identity. Macro packages opt into it through
ordinary dependencies. The SDK must not depend on it: a token-only macro needs
no syntax AST or parser dependency, and the first proc macro must build without
invoking itself or a quotation proc macro.

Lossless units and optional groups are not declarations, field types, or generic
binders. Provide one reusable library parser rather than making every derive author scan
the same syntax independently. This deliberately duplicates a bounded part of
the current Rust parser's grammar, not resolution, inference, MIR, or codegen.
The compiler and library own different AST types and may parse the same tokens
independently; the compiler still decides whether generated programs are valid.

The initial API consists of a local cursor and bounded Rock lexical/group
interpretation, span-aware parse errors, a `DeriveInput` entry point, and token
emission for supported nodes. Reuse supplied literal/classification views where
available, but do not require compiler-prepared declaration structure or a live
compiler just to parse an in-memory stream:

| Library-owned syntax | Initial responsibility |
| --- | --- |
| `DeriveInput` | Parse struct/enum kind, name, visibility, generic parameters/bounds, and ordered fields or variants from the supplied declaration tokens |
| Generic parameter/binder nodes | Represent names and supported kind/bound/default syntax; distinguish declaration binders from arguments when emitting an impl/type application |
| Field/variant nodes | Preserve source order, named/positional/nullary shape, visibility where applicable, field types, defaults, spans, and token provenance |
| Type nodes/token-preserving syntax | Parse the type grammar required by the initial derive fixtures; retain original tokens and explicitly diagnose unsupported syntax rather than guessing its structure |
| Token emission helpers | Convert unchanged or edited library AST nodes to output tokens, preserving copied spans/contexts and applying ordinary grouping/layout rules |

Function/default-expression bodies may initially remain captured token subtrees
where their boundaries are unambiguous; do not claim full expression parsing.
Opaque preservation is not permission to reinterpret an unsupported construct
as a different node. No new bounds, types, or visibility forms are introduced by
the library. A supported-grammar statement and negative tests accompany each
parser entry point, rather than labelling partial coverage a full Rock parser.

Library ASTs are ordinary Rock data that macros can inspect and transform. A
derive parses the original token input, builds an independent AST, and emits
ordinary impl items. It cannot mutate the compiler's preserved declaration or
query whether a field implements a trait, what an alias resolves to, or which
impl inference will select. Generate ordinary bounds/operations and let normal
compilation check them. Input names and unchanged syntax retain their original
contexts when emitted; never reconstruct a captured subtree with string output.

Share syntax fixtures with the Rust parser for the supported grammar. Cover
positive/negative parsing, indentation and nested commas, exact input consumption,
generic defaults/bounds, and parse/emit/parse round trips preserving token order,
exact trivia/spelling, expression grouping, source provenance, and binding
contexts. Surface library parse errors as structured macro diagnostics. Test failures and recursion/work
limits must not turn malformed input into compiler panics or infinite loops.

Initial derive grammar and emission are Stage C requirements. Full declarations,
expressions, patterns, general visitors/folders, and raw-source parsing grow
later as separately scoped library work. Quote-style conveniences may live with
the initial token helpers until a separate package is useful; do not clone every
crate boundary in Rust's ecosystem just to start this library.

### Foundation for a future self-hosted frontend

This parser is intended to become reusable infrastructure for rewriting Rock in
Rock, not a throwaway derive-only recognizer. Keep token data, parser cursors,
syntax nodes, and parse diagnostics usable in ordinary Rock programs/tests with
no active macro worker or compiler callbacks. Invocation-specific authority is
needed for emitted binding contexts, not for inspecting/parsing in-memory tokens.
Do not make AST construction depend on `MacroContext` or the proc transport.

Preserve Rock layout and symbolic operators faithfully. In particular, expression
support added later must not hardcode std operator existence/meaning or assume
a fixed std precedence table. It may retain unresolved operator syntax for a
later declaration-aware pass, just as semantic questions remain separate from
syntax in the current compiler.

The eventual path is bounded lexical interpretation/token parsing, wider grammar
coverage and Rock-written raw-source scanning, then semantic/compiler passes
under their own designs. The initial library consumes supplied lossless streams;
it need not implement full raw-source scanning or replace `lib/src/parser/`.
The Rust frontend's lossless preservation/capture-aware interpretation redesign
is required now, not deferred with self-hosting. A complete Rock-written lexer,
full Syn-scale grammar, bootstrap compiler, production-compiler migration, and
permanent AST/HIR design remain outside this delivery.

### Parsing boundary and explicit limitations

- Lossless traversal/spelling access, group replacement, token splicing, and
  macro-specific DSL grammars run locally in Rock with the SDK. No successful
  Rock literal/group interpretation is required for arbitrary block input.
- Syntax parsing/AST transformation lives in the ordinary Rock syntax library,
  not in the compiler-facing SDK or special derive request payloads. Initial
  parser coverage is deliberately smaller than full Rock syntax.
- Operator resolution, name resolution, inference, trait selection, and ownership
  checking remain compiler responsibilities, not syntax-library features.
- Formatting can scan its own brace/hole syntax and emit a literal-fragment
  descriptor; the compiler's Rock interpretation/parser processes that expression
  afterward. A derive invokes the library's local token-to-AST parser.
- There are no live compiler `parse_expression`, `parse_type`, or `resolve_name`
  services inside a worker. Library parsing of already available tokens is
  synchronous ordinary Rock code; deferred source fragments still cannot be
  inspected as tokens/AST before returning the final result.
- Rich expression/type transformations need the corresponding library grammar
  coverage. Supplied source units are immediately inspectable, unlike output-only
  fragment descriptors. Lexing an arbitrary newly constructed string locally
  would additionally require a Rock-written scanner, not automatically provided
  by a parser over existing units. Do not secretly restore RPC or promise that
  deferred fragments provide a synchronous parse API.

This is enough for block DSLs, structural derives, and library-owned interpolation,
not a claim that every conceivable syntax-analysis macro is supported immediately.
The work includes the substantial lossless Rust frontend boundary, shared
transport metadata, and a bounded Rock syntax interpreter/parser/emitter with
conformance tests, not an entire second semantic frontend.

### Literal views and deferred source fragments

Keep one compiler request and one final worker response. Prepare canonical
literal views and decoded-to-source byte mappings for literals already recognized
by Rock argument/declaration parsing before starting the worker, under the request
size limit; the SDK reads them locally. Do not pre-interpret arbitrary block text
as Rock merely to populate literal views: its quote characters may be DSL text.
Do not add live lexer/literal service requests, a callback broker, or a full
duplicate lexer merely to decode literals. Bounded local Rock syntax helpers
and the future self-hosted scanner are distinct library work described above.

For expression holes, retain an output-only source-fragment element in the shared
token stream. The worker can emit either:

- A reference to an input literal view and a checked decoded UTF-8 byte range,
  with invocation-site syntax context; the compiler extracts that exact text.
- Explicitly generated text with a permitted syntax context and generated-source
  provenance, for cases with no input source range.

After the worker exits, validate ranges/handles and scan these fragments into
the shared lossless representation, preserving the selected contexts and source
mapping, before capture-aware Rock interpretation/generated-output parsing. A
fragment is an emission splice, not a new runtime expression or an immediately inspectable list
of tokens in the worker. No synchronous compiler service is needed to emit
`count + 1` from a literal hole. The macro receives existing declaration tokens
directly when it does need to inspect syntax, as with derives.

Fragment boundaries must not accidentally glue adjacent tokens or change the
grouping intended by the output tree. Fragments are source text, not a host
request, file-loading override, forged identity, or pre-resolved HIR side channel;
any generated module declarations still go through ordinary source discovery.
Do not print and re-lex captured trees: their existing metadata remains intact.
Invalid generated Rock is an interpretation/generated-parse diagnostic at its
mapped location, not a rejection by the neutral preservation layer.
Literal mappings must handle multibyte characters and escapes; a fixed quote
offset applied to decoded byte indices is not sufficient. If the canonical
literal decoder is currently phase-local, extract that helper rather than
copying its rules into a new SDK subsystem.

Formatting-specific brace scanning, escaping policy, trait selection, buffer
construction, and evaluation strategy belong to the formatting macro/library.
The generic fragment mechanism never interprets `{...}` as interpolation. Ordinary
Rock string syntax and decoding rules remain unchanged despite the lexical-layer
redesign: inline formatting arguments must still be valid Rock strings, including
escaping quotes inside embedded expressions. Arbitrary quotes in a captured DSL
block are different because that block is not interpreted as a Rock string.

## 7. Process protocol, diagnostics, and trust

Evolve the existing bounded subprocess request/response protocol rather than
loading native macro code into the compiler process or introducing a session/RPC
framework:

1. Compiler sends the selected export identity, kind/category, invocation
   context, one shared lossless lexical stream with origin/context segments,
   recognized literal/group/argument views where applicable, capture range/layout
   metadata, and authorized handles, then closes the request stream. Do not
   introduce a raw-string input alternative. Derives contain original declaration
   streams, not a compiler AST projection; block quotes need not be Rock literals.
2. Worker sends one final expansion result with output trees/fragments and/or
   diagnostics and exits; success requires a valid response and successful
   process termination. No intermediate messages or compiler callbacks exist.

Reuse the current encoding/options where adequate, extending its versioned
schema only for required metadata; there is no independent stable wire standard
or multi-version negotiation requirement. Specify the actual encoding/options
and verify the Rust compiler and Rock SDK against shared golden messages. Bound
lengths before allocation; reject unknown wire variants, trailing/truncated data,
invalid UTF-8/ranges/coverage and source/context/dependency handles. Unknown source
characters are preserved data, not unknown wire variants. Never deserialize
unchecked compiler identities or assume that Rust memory layout is a wire format.

The current Rust contract and shared golden-message locations are specified in
[the worker wire contract](2026-10-19-macro-worker-wire.md); SDK interoperability
is established separately by the staged acceptance plan.

Stdout is protocol-only. Capture bounded stderr for developer diagnostics without
treating it as expansion tokens. Keep one fresh worker per invocation initially;
worker pooling is not required and must not leak mutable global macro state.

Retain explicit limits, starting from the existing 1 MiB per-message and
10-second per-invocation limits, with compiler-controlled overrides for tests.
Also bound lossless spelling/trivia bytes, lexical units, interpretation/group/
fragment depth, matcher work, and total compilation expansion work. The wall-clock
deadline includes writing the request, reading
the response, and shutdown, not just waiting for the process to exit. Fragment
scanning/interpretation shares the ordinary compiler expansion/token budget; nested
fragments cannot bypass limits by representing a large stream as one element.

On timeout, cancellation, broken pipe, malformed output, oversized output, crash,
or nonzero exit, terminate/reap the worker and close/join transport resources
without an unbounded wait. Handle descendants retaining pipe handles; killing
only the direct child then blocking in a read-thread join is not adequate.
Report the invocation, export identity, cause, and bounded stderr context.

The subprocess is crash isolation, not a security sandbox. Macro packages run
native host code with the user's permissions; the existing `Stdio` capability
tag does not restrict their filesystem/network access. Document that trust
boundary, preserve OS permission errors, never invoke a shell to launch a macro,
and provide an explicit compiler/CLI no-proc-macro-execution mode. That mode may
inspect/import metadata and expand declarative macros, but a proc invocation
fails clearly instead of secretly starting a process.

Stable traversal and fresh workers support reproducible behavior, but cannot
make arbitrary native IO deterministic. Cache host build products using tracked
inputs; do not cache/replay proc expansion results in this delivery. A future
tracked-IO or sandbox design requires its own specification.

Preserve source snapshots, context, and expansion ancestry beyond parsing into
resolution, inference, borrow checking, and codegen diagnostics. Captured tokens
point at caller source, literal-derived tokens at the correct string range,
and generated-only failures at the invocation with expansion notes. Debug
expansion output should show identities/origins without being used as semantic
input; the existing expanded-output and `rock expand` paths must use the same
engine as normal compilation when given equivalent dependencies.

## 8. Consumer proof boundaries

### Formatting proof

An ordinary external macro package must be able to accept a string token
containing `Hello {name}`, extract `name` with invocation-site binding, and emit
an expression that calls an explicitly supplied ordinary helper library. A
second case must tokenize an embedded expression such as `count + 1` without
hardcoding the existence or meaning of `+` in the infrastructure.

Use a small test helper library, not compiler-owned std loading or a production
formatting subsystem. Test a field without formatting support and a missing
runtime helper dependency as normal diagnostics. A missing name inside the
literal must underline the corresponding literal subspan, including after an
escape or multibyte character.

For the proof macro, evaluate/format holes once, left-to-right, borrow named
values for formatting, and release temporaries normally; calls inside a hole
retain their ordinary consuming behavior. Test caller names that collide with
builder/helper names. These are proof-macro semantics, not evaluation guarantees
imposed on all user macros: macros can intentionally duplicate or discard input.

The production formatting trait, growable buffer API, format specifiers, and
user-facing interpolation policy belong in a separate consumer specification.

### Derive proof

Use an external Rock-authored derive to emit an impl for an ordinary explicitly
declared test trait on a struct and an enum, including generic binders and bounds.
The provider is not named std and the trait is not compiler-recognized. Prove
that normal typing, visibility, coherence, ownership, and source diagnostics
apply to the emitted code. A built-in synthetic impl or Rust-only test host does
not prove the public derive authoring path.

### Indented DSL proof

Use an external Rock-authored function-like macro that receives an indented
block and checks its exact lexical spelling/layout, then emits an ordinary
expression using the same SDK result contract as the formatting fixture. Input
must include HTML-shaped tags, whitespace/newlines, an apostrophe such as
`Don't`, unmatched quotes/brackets, `//` and `/*` spellings, otherwise unsupported
symbols, and multibyte text. None may fail Rock lexing before the worker runs.
A following dedented Rock binding must remain outside the captured block even
after an unterminated quote/comment-like sequence inside it.

This is not a production HTML parser. Prove a library-defined interpretation and
a structured diagnostic at a precise DSL subspan, not merely a compiler builtin
that accepts one markup example. Also exercise item-category block output,
literal `%macro` text that must not pre-expand, and an outer macro that forwards
a nested block through generated Rock without losing contexts or payload text.
An identity result that places the arbitrary DSL text directly in ordinary Rock
must fail normally; lossless acceptance of input does not make that output valid.

## 9. Delivery sequence and acceptance

The [staged implementation plan](2026-10-19-macro-infrastructure-plan.md)
breaks these stages into small dependent slices with focused test gates; it
records sequencing, not implementation progress or a replacement for beads.

### Stage A0: lossless frontend foundation

Deliver neutral source preservation, exact source/trivia coverage, metadata-safe
slices/splices, optional Rock token/group views, and capture-aware interpretation
before reusing the normal syntax parser. Refactor the eager whole-file strict
lexer/parser boundary; preserve current Rock lexical behavior and diagnostics
outside explicitly captured macro input. Test malformed/unfamiliar text as
preservable data separately from its rejection when interpreted as Rock. This is
a substantial frontend change, not an added catch-all `TokenType` variant or a
new raw-block input mode. It remains Rust-implemented initially; full self-hosting
is not a gate.

### Stage A: common token and expression expansion foundation

Deliver ordinary-call and indented-block invocations, deterministic dedent/capture
rules, exact generated-expression parsing, shared lossless input/layout, module
traversal, explicit source-module macro imports, and hygienic resolution through
lexical interpretation. Reuse deterministic bounded expansion passes; do not
make cross-crate declarative publication or an incremental scheduler a gate.
Do not claim expression macros complete while contexts disappear during parsing
or only the root module expands.

### Stage B: usable host proc macros

Deliver the library flag, source-declared exports, host-aware ordinary dependency
builds, minimal proc-only artifact validation, Rock SDK/dispatcher, literal views,
deferred fragments, one-shot protocol, process lifecycle, and execution-disable
mode. Run a Rock-authored function-like macro through `rock build`/`rock run` and
artifact-level `rockc` tests. Complete the formatting feasibility proof without
live compiler callbacks, facade re-exports, or a new transport framework. Complete
the indented DSL proof using the same stream/entry contract, not a raw-string
worker alternative or Rock-token-only block preprocessing.

### Stage C: derive attachment

Deliver `%derive` attachment and `macro derive Name = ...` source declarations,
original declaration token retention, consume-once expansion/export validation,
and a Rock-written syntax library covering the derive proof's declaration/type
grammar and token emission. Run an external Rock derive through that library.
No compiler declaration projection or general attribute engine is required.
Full Syn coverage and a self-hosted frontend are not completion gates;
attribute-like transforms remain explicitly unsupported. Stage B success alone
is not derive support.

The following acceptance families must be mapped to named tests and retained
command results by the implementation; this draft records requirements only.

| Family | Required observations |
| --- | --- |
| Lossless frontend | Exact UTF-8 coverage including whitespace/comments/CRLF and unfamiliar symbols/NUL, neutral preservation of unterminated quotes/comments and unmatched delimiters, metadata-safe slices/splices, bounded scanning, unchanged ordinary Rock token/spacing/literal/layout behavior and error spans |
| Syntax/category | Ordinary Rock comma/grouping/zero-argument call rules, distinct bare-header block capture, multiline ordinary-call disambiguation, expression and item block results, nested macro input not pre-expanded, postfix behavior, exact result consumption, item-vs-expression mismatch, rejection of unbounded inline DSL input |
| Block boundaries | Matching physical dedent/EOF, blank lines, comment-looking body lines, nested indentation, source-policy spaces/tabs, CRLF, no trimming, no width overflow, unmatched quote/comment cannot swallow following Rock, no false invocation inside ordinary strings/comments, generated/nested forwarded blocks |
| Declarative behavior | Existing item cases, first matching arm/full input, grouped expression precedence through forwarding, distinct equal-spelled captures, flat repetition, explicit nested-repetition rejection, bounded ambiguity/matching |
| Modules/resolution | Root/inline/file modules, declaration order, generated modules/imports/definitions, direct external proc imports/qualified calls, collision/privacy/unknown-path diagnostics, unresolved import cycles, explicit diagnostics for deferred declarative artifact exports and macro facade/glob use |
| Hygiene | Caller/template local collisions, nested and duplicated captures, fresh proc locals, intentional call-site names, definition helpers under dependency renaming/shadowing, no private-item authority escalation |
| SDK/protocol | Rock SDK/compiler golden-message interoperability, same lossless stream type for inline/block/item/derive input, exact spelling/trivia and local stream/group/cursor/splice operations, argument boundaries including nested commas, fresh versus forwarded/reinterpreted identities, one request/one response, recognized literal views without classifying DSL quotes, escaped/Unicode subspans, deferred-fragment scanning/interpretation/budgets, invalid source/context/dependency handles |
| Process failure | Missing executable, wrong host/protocol/compiler/artifact identity, nonzero exit, crash, broken pipe, truncated/trailing responses, byte/token/work limits, timeout/cancel, descendants retaining pipes, stderr/stdout misuse |
| Build/artifacts | Source-declared names/kinds and ordinary exports, no manifest export table, `[lib].proc_macro` validation, ordinary dependencies built in correct role, Rock-authored executable, proc-only artifact without dummy target object, missing runtime helper dependency, cycle diagnostics, relocation/content validation |
| Host separation | Build-planner tests with distinct host/target identities prove no target executable is selected; runnable foreign-target acceptance is required only when the existing toolchain supports that target, otherwise record that limitation |
| Recursion/budgets | Direct/mutual recursion, generated derives/modules, duplicated-span invocations, wide sibling expansion, matcher non-progress, stable errors independent of unrelated expansion order |
| Formatting proof | Literal identifier/arbitrary-expression extraction, correct caller resolution, exact subspan errors, normal missing-bound/type errors, once/left-to-right evaluation, borrowing, temporary destruction, helper collision |
| DSL proof | External Rock worker sees exact arbitrary block text before Rock interpretation, library-defined parse and subspan diagnostic, expression/item outputs, nested forwarding with hygiene, invalid direct DSL-as-Rock output rejected, no compiler HTML knowledge or second input ABI |
| Syntax library | Rock-written bounded lexical/group interpretation and token-to-AST parser used by the derive fixture, explicit supported grammar and unsupported cases, shared Rust-interpreter/parser conformance fixtures, lossless parse/emit/parse round trips, malformed-input diagnostics/work limits, no active macro context needed for standalone parsing |
| Derive proof | `%derive` with qualified/comma-separated paths, blank lines/comments and consecutive directives, missing/intervening/unsupported targets, reserved directive name, library AST fidelity for struct/enum names/field order/named or positional variants/generic defaults/bounds/visibility, original token/context retention, declaration retained once, consume-once/generated attachment recursion, duplicate/wrong-kind errors, ordinary impl rejection |
| Semantic integration | Unchanged inference, operators, borrow/drop/unsafe rules; generated return/break use the surrounding lexical context; no macro-only bypass of checked HIR/MIR |
| Trust/inspection | No worker when execution is disabled or only metadata is inspected, no unqualified export injection, explicit trust documentation, no expansion-result cache claiming deterministic IO |

For artifact acceptance, build providers once, remove their original source
trees from the consumer fixture, and compile consumers using only packaged
artifacts/executables/dependencies. Verify provider bytes stay unchanged; include
synthetic obsolete/corrupt artifacts that reject before executing any worker.

Run the smallest relevant lossless-lexer/interpreter/parser/macro/SDK/build tests
first, then serialize the broader gates: `cargo test -p rock-lib`, affected shared-manifest/CLI crate tests,
`cargo build --release`, and `cargo clippy --workspace --all-targets`. A future
SDK Rust workspace member, if needed for wire helpers/tests, must be included
explicitly in those gates. Record existing warnings separately from failures.
Do not run test suites concurrently or rerun a long suite merely to recover its
output; retain a single log/receipt. Formatter execution and formatting checks
remain excluded under the current repository instruction.

Completion means the named stage's requirements and negative controls pass on
the final source snapshot. Infrastructure completion is A0, A, B, and C, not
an enum addition, parser-only support, a passing subprocess fixture, or a claim
that the separate production formatting/derive libraries have shipped.
