# Rock compiler performance: `b8b584cd` → `514ee6de`

## Baseline and limits

Ryzen 9 7945HX, 16 physical cores, 32 hardware threads, Linux, `/tmp` on tmpfs. Both compilers built from source using the same Rust toolchain and release profile. The CLI measurements invoke rockc directly in fresh processes with warm filesystem pages. Rock program optimization is O0 unless specified; this is independent of the host compiler build profile. Standard library built independently for each revision. This is a one-machine experiment, not a CI budget or an estimate of fleet p95.

`measure.py`: six alternating rounds; first discarded for phase medians. `wall` includes startup, destruction, artifact writing and anything outside `PhaseTimer`. The first phase called `load+parse` includes loading all external artifacts; `emit` includes the system linker if linking is enabled. Phase medians need not sum to median wall time.

| Bare main → object | 11.76 ms | 12.30 ms |
| Identical main + unused std → object | 285.01 ms | 297.59 ms |

Integration A/B (independent test executables and std caches; fixed 16 threads; skipped both tests newly added by the PR on current, leaving 1,159 named tests including the amended artifact assertion): first runs 67.11/68.52s; warm pre-PR 46.74/41.02/45.78s; current 47.69/47.99/51.31s. All passed. First runs and warm runs measure different workloads: the std cache key includes executable metadata. A warm disk cache avoids compiling std, but not importing it per compilation. Historical logs have different workloads and unknown contention; useful context, not a baseline for attribution to one change.

## Is the PR, or the host compiler build, the bigger lever?

`cross.py` swaps old/current std artifacts between both release compilers while compiling identical `main = -> 0` to an object (randomized order, 11 measured rounds). Median wall times, old/new artifact respectively: old compiler 292.91/297.53ms; new compiler 293.26/294.95ms. Same old artifact, different compiler: only 0.35ms difference. The new artifact adds 1.69–4.62ms at these medians. There is no evidence here of a large parser regression; this crossover cannot apportion the whole suite's slowdown.

`scaling.py`: same current source, Rust host `opt-level=z` versus `3`, same generated Rock O0 output setting, no link, five measured alternating rounds per input. Hello with std: 296.89→183.99ms (-38%); std itself: 21.89→15.96s (-27%); 512 functions: 491.74→305.52ms; 512 impls: 1.093s→580ms. Recommend a release compiler profile optimized for speed; check packaging size, clean Rust build time, and the full suite before selecting repository-wide defaults. These are compiler runtime gains, not predictions of the same percentage improvement in parallel integration wall time.

**Scaling:** With the speed profile, increasing from 128 to 512 independent typed identity functions (only one called) multiplies inference time from 12.48 to 171.84ms (13.8×); 128→512 impls of one trait on distinct types (only one used) takes 28.91→425.96ms (14.7×). Even the faster compiler is doing substantially superlinear frontend work in these workloads. This does not by itself prove the asymptotic complexity of an individual routine.

## What to change, and how to judge it

1. **Make small programs pay for the std they use.** `lib/src/pipeline/frontend.rs` loads externs before parsing the entry; `crate_system/extern_artifacts.rs` orders dependencies, then `crate_artifact/load/mod.rs` decodes the payload, reconstructs products, remaps IDs, interns types and stages context changes. On unused std, *load+parse alone* is 162ms; even after it completes, infer and mono still take 70 and 36ms. First add nested spans and counts (bytes, decoded declarations/bodies, remapped IDs). For the integration runner and LSP, reuse validated immutable portable products, keyed by content and schema; keep remaps, diagnostics and mutable inference state per compilation. For single-shot CLI speed, split eagerly needed declarations/operators/impl headers from indexed generic bodies. Load bodies on demand for specialization; retain corruption checks and deterministic identity semantics. An in-process cache alone cannot fix CLI startup. Measure unused std, one used generic, transitive dependency graphs, memory per parallel test, and edited-dependency invalidation independently.

2. **Give the inference worklist less work.** In `lib/src/infer/quiescence.rs`, `declaration_bounds` traverses functions, impls and traits inside a structural work item and again in final component solving. SCC membership is discovered by rescanning the map per component. Substitution generation changes can enqueue *all* previous components; authority wakeups scan peer obligations. Std inference measured 15.51s (71% of wall); this identifies a phase, not a measured percentage for any one loop. First count bound rebuilds, queue insertions/repeated pops, obligations examined/woken and useful substitutions. Precompute SCC membership in one pass, then cache bounds by actual declaration changes, and deduplicate pending work. Only then move to reverse dependency edges. Preserve defaulting order, generalized bounds and diagnostic precedence; compare inferred public signatures and negative tests, not just successful builds.

3. **Separate check, emit and run.** `pipeline/mod.rs::analyze` stops before MIR; `compile_should_pass` in the integration harness sets `no_link` but still emits an object. Add a check-through-MIR endpoint for positive ownership/type tests, with identical borrow/contract diagnostics. Frontend-only tests may use `analyze`; execution, linker, optimization and codegen tests must still exercise those paths. Most ordinary compile-and-run tests invoke a binary directly: the special process-group helper’s 10ms sleep is not universal. Measure harness wall and CPU, cold/warm, fixed thread count. A faster harness is useful but not evidence of a faster user compiler.

4. **Avoid copying IR where ownership already transfers.** In `mono/process.rs::process`, functions are cloned into a vector before clearing `program.functions`; every impl is cloned before collection. Preserve stable ID order but move owned function entries, and register impl headers by ID separately from materializing bodies. Count bodies available, cloned, demanded and emitted, plus peak RSS. Start with the tiny std consumer: mono costs 36ms even when the user's code does not use std. In `pipeline/backend.rs`, splitting `mir-bodies` from `mir-build` already helps: the former alone costs ~1.38s on std. Measure retained body counts before redesigning MIR. Keep borrow checking and runtime agreement; this experiment does not identify them as primary costs.

5. **Target other scaling problems with workload-specific experiments.** `traits/coherence/validation.rs` compares impl pairs before eliminating different trait IDs. Bucket by trait and arity first, then index disjoint nominal heads while retaining blanket candidates. For multi-dependency loading, staging by cloning the accumulated `CrateContext` on each import can scale with all previous imports; stage an insertion delta instead. Verify no partial mutation on bad artifacts. Test doubling dependency count, impl count, and blanket-impl fraction separately. Neither code observation proves it dominates ordinary builds.

6. **Treat edit latency as its own product.** `rock/src/artifact.rs::artifact_is_fresh` spawns `rockc --validate-artifact` before checking source mtimes; that command deserializes the payload. Check cheap staleness first; amortize validation of identical bytes without accepting corrupt or replaced files. `rock-lsp/src/main.rs::analyze_target` shares a result within a refresh but invokes whole-frontend `analyze` for a changed target. Start with immutable dependency reuse, then unchanged parsed modules; only introduce per-item incremental inference once dependencies and invalidation are explicit. Benchmark no-op builds, leaf and public-signature edits, and time to diagnostics separately. Current measurements do not quantify those scenarios.

7. **Leave LLVM/link, general parser rewrites and compiler-wide parallelism behind those changes for now.** Hello's O0 object vs executable differs by ~20ms; O3 vs O0 executable differs by ~5ms here. This does not extrapolate to a large optimized application. The tests use O0 by default. For larger workloads, split LLVM passes, object writing and `cc` timing and measure release program throughput as well as build time. Parallelizing fine-grained work before removing redundant scans risks multiplying memory pressure under parallel tests.

## Suggested acceptance measurements

Track warm single-process and fresh-process compilation separately; publish medians, ranges and RSS, with compiler and generated-program profiles recorded independently. Key workloads: minimal no-std, unused std, generic-heavy consumer, full std, one production-sized application, changed and unchanged dependency graphs, LSP single-body edit, and full fixed-concurrency integration tests. Keep the baseline input set fixed across revisions. Use `ROCK_TIME_PHASES=1` plus a wall clock; do not label the initial bucket “parser time.” Re-run full release correctness tests for each implementation change; retain determinism, ownership diagnostics, artifact corruption/invalidation checks and output equivalence.
